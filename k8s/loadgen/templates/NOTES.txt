Each `loadgen` role reads one HOCON env.conf from its own
`<component>.config.existingSecret`, mounted at CONFIG_PATH, and this chart
generates neither it nor the `${VAR}` values it references (see values.yaml's
`secrets` block). `role` lives in that file, which is why the driver and the
coordinator take one Secret each rather than sharing one.

Whatever the role, every one of those files must set a top-level `env`.
VersolaApp reads it (EnvName, and the `env` label on every log line) before a
single loadgen-specific field is decoded, so a file without it is not a failed
probe but a CrashLoopBackOff on boot, on the coordinator and every driver
alike:

    zio.Config$Error$MissingData: (Missing data at env: Expected env to be set)

This chart cannot check that for you -- it never reads the Secret. What it does
supply is ENV_NAME={{ .Values.envName }} on both roles, so the file can say

    env = ${ENV_NAME}

and let this release name the environment rather than the Secret.
{{- if .Values.driver.enabled }}

The driver fleet is a StatefulSet of {{ .Values.driver.replicaCount }} shards. Its env.conf must read the
injected ordinal, or every driver runs as shard 0:

    role = driver
    shard { index = ${SHARD_INDEX}, count = ${SHARD_COUNT} }

It must also carry a `clients` block naming the clients that were provisioned
(`mobile-otp`, `mobile-otp-password`, `mobile-passkey`, the web preset, the
requested scope and the OTP length). A driver holds no `provision` block, so
nothing else in its file states which clients it may authenticate as.

{{ .Values.driver.replicaCount }} must equal the `seed.shard-count` the population was seeded with:
`vu_users.shard` holds `id % shard-count`, written at seed time, so changing
the replica count without the re-shard UPDATE leaves part of the population
owned by no driver and part owned by two.
{{- end }}

Every pod carries prometheus.io/scrape annotations on its diagnostics port. The
boards in k8s/loadgen/dashboards/ select on `namespace`, `job` and `pod`, none
of which any Versola metric emits itself -- if your scrape configuration drops
them, the fleet-wide sums still work and the per-pod breakdowns come up empty.
