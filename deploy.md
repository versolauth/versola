# Deployment

How Versola is deployed to the shared production host (`id.versola.kz`). For local development
see [`develop.md`](develop.md).

> **Scope.** This is a runbook for the *current* production deployment: a single VPS that also
> serves the marketing site, blog, docs and Grafana. Versola runs there under
> [`versola-cli`](https://github.com/versolauth/versola-cli) — `versola configure vps`,
> `versola migrate`, `versola up` — which pulls the release, generates its configuration, resolves
> secrets against OpenBao and starts everything, including Versola's own reverse proxy. Commands
> assume you are logged in on that host as the deploy user (`debian`), with `sudo`.
>
> For Kubernetes, see [`k8s/README.md`](k8s/README.md). The two paths share the configuration
> *format* and nothing else.
>
> **History.** Until September 2026 production was deployed by a GitHub Actions `Deploy` workflow
> from a hand-maintained `/opt/versola/docker-compose.prod.yml`, with configs from the private
> `env-config` repository and all Versola routing in the host nginx. All of that is retired — see
> [11. Retired deployment path](#11-retired-deployment-path).

## 1. Topology

| Component | How it runs | Managed by |
|---|---|---|
| PostgreSQL 18 | native, `apt` + systemd, `127.0.0.1:5432` | `systemctl` |
| `auth`, `central`, `edge` | Docker, Compose project `versola-vps`, `network_mode: host` | `versola-cli` |
| `versola-proxy` — Versola's reverse proxy | Docker, official `nginx:1.30-alpine`, same Compose project, listens on `127.0.0.1:2821` | `versola-cli` (config generated by the CLI) |
| OpenBao (secrets) — `versola-openbao-vps` | Docker, same Compose project, `127.0.0.1:8200` | `versola-cli` |
| Host nginx — TLS, static sites | native, `apt` + systemd, ports 80/443 | the [`nginx`](https://github.com/versolauth/nginx) repo, deployed by its own workflow |

A request to `https://id.versola.kz` goes:

```
browser ──443──▶ host nginx (TLS only) ──▶ 127.0.0.1:2821 versola-proxy ──▶ auth  127.0.0.1:8080
                                                                        └──▶ edge  127.0.0.1:8095 ──▶ central 127.0.0.1:8090
```

The host nginx's `id.versola.kz` block does nothing but terminate TLS and forward everything to
`127.0.0.1:2821` (see [3.7](#37-host-nginx)). **All of Versola's routing** — which path goes to
`auth` and which to `edge`, the admin console, the legacy redirects — lives in `versola-proxy`,
whose configuration `versola-cli` generates on every `configure`.

This is `versola-cli`'s `--proxy external` mode, used because this host already has a web server on
80/443. On a server of its own, the default `--proxy nginx` makes `versola-proxy` own 80/443 and
obtain a Let's Encrypt certificate itself; see versola-cli's README, "Deploying to a VPS".

Because the services use `network_mode: host` with `BIND_HOST=127.0.0.1`, each binds a localhost
port on the host and there is no Docker network between them. Nothing binds to `0.0.0.0` except the
host nginx.

### Ports

| Service | App (`PORT`) | Additional (`APORT`) | Diagnostics (`DPORT`) |
|---|---|---|---|
| `auth` | 8080 | 8082 (Account Settings, internal) | 8081 |
| `central` | 8090 | — | 8091 |
| `edge` | 8095 | — | 8096 |
| `versola-proxy` | 2821 | — | — |
| OpenBao | 8200 | — | — |

The source of truth is the generated `compose.yml` in the active bundle (next section). The
Dockerfiles `EXPOSE 8080 9345`, but with `network_mode: host` `EXPOSE` is inert — `PORT`/`DPORT`
decide.

### Where things live on the host

| Path / object | What it is |
|---|---|
| `~/.versola/active/state.json` | which deployment is live: target, version, bundle, `--auth-url`, proxy mode |
| `~/.versola/active/bundle-*/` | one directory per `configure` run: `compose.yml`, `proxy.yml`, `auth.conf`/`central.conf`/`edge.conf`, `*.secrets.env` (mode `600`), `openbao.hcl`, `central-ui/` (the admin console), `proxy/` (nginx config) |
| `~/.versola/openbao/vps.json` | AppRole credentials `versola-cli` uses to read/write secrets |
| `~/.versola/openbao/vps-admin.json` | OpenBao root token + unseal key (lets `configure` unseal OpenBao itself). **Keep a copy off the host** — neither value is recoverable if lost |
| Docker volume `versola-openbao-file-vps` | OpenBao's data (all secrets). Survives `down`/`uninstall` |
| Docker volume `versola-acme-vps` | Let's Encrypt state for `--proxy nginx` (unused in `external` mode) |

Everything in a bundle is **generated** — do not hand-edit it. The next `configure` writes a new
bundle and the old ones are removed once nothing runs from them.

### Why these three services

- **`central`** — configuration store: tenants, clients, scopes, roles, permissions, forms, JWKS.
  Serves the admin API and bootstraps the initial dataset on an empty database.
- **`auth`** — the OAuth2/OIDC endpoint users hit (`id.versola.kz`). Signs tokens; syncs its
  client/scope configuration *from* `central`.
- **`edge`** — authorising reverse proxy in front of `central`'s admin API, and the login entry
  point for the admin console.

**Startup ordering matters:** `auth` and `edge` block on their initial config sync from `central`
(up to two minutes), and are not serving while they wait. `versola up` starts `central` first, waits
for its `/readiness`, then starts `auth` and `edge`, waits for theirs, and starts `versola-proxy`
last. See [9.5](#95-authedge-never-become-ready-after-restarting-the-whole-stack-together) for what
happens if you restart everything at once by hand.

### The admin console (central-ui)

`central-ui` is a static SPA. It is **not** a separate deployment: CI builds it into the
`versola-tools` image of each release, `versola configure` copies it into the bundle
(`central-ui/`), and `versola-proxy` serves it at `/central/admin/`. The console on the host is
therefore always the one from the running release — deploying a release deploys its console.

The console and its edge API share the `id.versola.kz` origin via path routing in `versola-proxy`
(`internal/proxy/templates/routes.conf` in `versola-cli`):

| Path on `id.versola.kz` | Routed to | Purpose |
|---|---|---|
| `/central/admin/` | static `central-ui/` from the bundle | the SPA itself |
| `/central/permissions/me` | `edge` | the caller's permissions; rewritten back to `/permissions/me` |
| `/central/…` (everything else) | `edge` | admin API; rewritten to `/resources/central/…` |
| `/login/`, `/complete`, `/logout/…` | `edge` | OAuth login flow entry point, callback, edge-initiated logout |
| `/resources/`, `/permissions/` | `edge` | edge's own routes, kept for non-console clients |
| `/admin`, `/admin/…`, `/central`, `/central/` | `301` → `/central/admin/…` | legacy/bare locations |
| everything else | `auth` | the OIDC endpoints |

Redirects are relative (`absolute_redirect off`), so they stay correct behind the host nginx.

Sharing one origin is deliberate: the `EDGE_SESSION` cookie and the edge's `401`+`Location`
re-auth redirect are same-origin, so there is no CORS or `SameSite=None` handling to get wrong.

**Why everything sits under `/central`.** The `EDGE_SESSION` cookie is scoped with
`Path=/central` so that the session belongs to this application rather than to the whole domain —
a second app behind the same edge can then hold its own independent session. A browser only sends
a cookie to URLs *beneath* its path, so every URL the console touches has to share that prefix:
its assets (`/central/admin/`, baked in by `vite.config.ts`'s `BASE_PATH`), its API calls, and its
permissions lookup. The proxy unwraps the prefix before forwarding — `/central/{x}` becomes edge's
real `/resources/central/{x}` route and `/central/permissions/me` becomes `/permissions/me` — so
`edge` itself knows nothing about this scheme. `/login` and `/complete` stay at the root because
neither reads the cookie (`/complete` only *sets* it, and a `Set-Cookie` may declare any `Path`
regardless of the URL that issued it).

The browser-facing login preset (`central-admin`) is seeded from the generated `central.conf`
(`bootstrap.presets`) with `redirect-uri = <auth-url>/complete`,
`post-login-redirect-uri = <auth-url>/central/admin/` and `cookie-path = /central`. Seed values are
applied once, on `central`'s first bootstrap against an empty database — **changing them later has
no effect on an existing database**, where the preset must be changed through the console or by
SQL. The `central-admin` client's `redirect-uris` must contain only `https://id.versola.kz/complete`
in prod.

An unauthenticated visit to `/central/admin/` has no session cookie, so `edge` can't tell which
login to send the browser to (the preset id lives in the cookie). `central-ui` handles that itself:
on a `401` without a `Location`, it navigates to `/login/central-admin`.

The console's bundle is always named `versola-admin.js` (no content hash), so the proxy serves
`/central/admin/` with `Cache-Control: no-cache` — browsers revalidate on each load and pick up a
new release immediately.

**When changing the cookie path,** note that a cookie is identified by name + domain + path, so an
`EDGE_SESSION` left over at the old path is a *different* cookie that a logout scoped to the new
path will not clear. The simplest cure is to clear cookies (or use a private window) once after the
switch.

**First admin login.** `AuthBootstrapService` (in `auth`) creates the `admin` user, grants it the
`oauth-admin` role (full permissions), and sets a **temporary** password from `auth.conf`'s
`bootstrap.password` — on vps that is `ADMIN_BOOTSTRAP_PASSWORD`, generated once and kept in
OpenBao. `versola up` prints the exact file to read it from (the current bundle's
`auth.secrets.env`; right after a `configure` an older bundle may still exist next to it, holding
the same value):

```bash
grep ADMIN_BOOTSTRAP_PASSWORD <bundle printed by versola up>/auth.secrets.env
```

It is valid **24 hours**; logging in with it forces a set-password step. If it expired before
first login, restart `auth` (`docker restart versola-auth`) and bootstrap sets a fresh 24-hour one
(log line: `Set temporary bootstrap password for admin user 'admin'`).

**More admin users.** Console → **Users** → **Create User**, then **Edit Roles** → `oauth-admin`
(or a narrower role), then **Reset Password**. In prod the temporary password can only be
*delivered* — by email or SMS; showing it on screen is offered only outside prod. Neither SMTP nor
an SMS provider is configured on this host yet (see [10](#10-known-gaps)), so for now additional
admin accounts can't receive a password.

## 2. Prerequisites

- Docker and the Compose plugin on the host. `versola doctor --target vps` checks both, plus
  memory and disk.
- PostgreSQL 18 reachable at `127.0.0.1:5432`, with superuser access (`sudo -u postgres psql`).
- `versola-cli` on the host:
  ```bash
  curl -fsSL https://raw.githubusercontent.com/versolauth/versola-cli/main/install.sh | sh
  export PATH="$HOME/.local/bin:$PATH"   # the installer can't change the current shell
  ```
  (installs to `~/.local/bin`; if that isn't on `PATH` yet, also add the `export` line to
  `~/.bashrc` (or `~/.zshrc`) as the installer suggests. `versola upgrade` updates the CLI later).
- Published images in `ghcr.io/versolauth/` (`versola-tools`, `versola-auth`, `versola-central`,
  `versola-edge`) — all public, so the host needs no `docker login`. `versola-tools` of the release
  must ship the admin console (every release since the console moved into it does; `configure vps`
  refuses an older one with a clear message).
- In `--proxy external` mode (this host): a web server on the same host that forwards the domain to
  `127.0.0.1:2821` — here, the host nginx ([3.7](#37-host-nginx)).

## 3. First-time setup

What follows is the order for a **fresh** server. The production host has been through it already;
routine releases are [4](#4-deploying-a-new-version).

### 3.1 Check the machine

```bash
versola doctor --target vps
```

### 3.2 Configure

```bash
versola configure vps <version> \
  --auth-url https://id.versola.kz \
  --postgres-host 127.0.0.1:5432 \
  --proxy external
```

- `<version>` is the release tag **without** a leading `v` (see [Tag naming](#tag-naming)).
- `--auth-url` must be exactly the origin browsers use — scheme and host, no path, no default port.
  The CLI rejects anything else (a mismatch would break passkeys and redirects).
- `--proxy external` because this host already serves 80/443; omit it (default `nginx`) on a
  dedicated server.

`configure` pulls `versola-tools:<version>`, generates the bundle, starts OpenBao and — on the
first run — **provisions it automatically**: init with a single unseal key, unseal, KV v2, AppRole,
a policy limited to `secret/data/versola/vps/*`. The root token and unseal key are saved to
`~/.versola/openbao/vps-admin.json` (copy them somewhere safe, off the host), the AppRole
credentials to `~/.versola/openbao/vps.json`. It then resolves every secret: an existing value in
OpenBao wins; a missing one is generated and stored. Nothing of Versola itself is started yet.

If you would rather set OpenBao up yourself, pass `--setup-openbao` and follow
[`develop.md`](develop.md#secrets-openbao) — the CLI then never touches OpenBao's admin API and
needs `versola secrets login vps …` first.

### 3.3 Database, role and schemas

All three services share **one** Postgres database, `auth`, isolated by schema — not three
databases. The generated configs already point each service at its own schema
(`jdbc:postgresql://127.0.0.1:5432/auth?currentSchema=central`, etc.).

On a first `configure` against an empty OpenBao, the Postgres password is generated then and there,
so the role can only be created **after** `configure`. `configure` prints the exact statements:

```
Postgres: this was the first configure against this OpenBao, so a new password was
generated for Versola's Postgres role and stored there. …

  CREATE ROLE "versola_app" WITH LOGIN PASSWORD '…';   -- if the role doesn't exist yet
  ALTER ROLE "versola_app" WITH PASSWORD '…';          -- if it already exists
```

As the `postgres` superuser (`sudo -u postgres psql`), run the `CREATE ROLE` line (or `ALTER ROLE`,
if the role was created earlier with a password of its own), then:

```sql
CREATE DATABASE auth OWNER versola_app;
\c auth
CREATE SCHEMA IF NOT EXISTS auth    AUTHORIZATION versola_app;
CREATE SCHEMA IF NOT EXISTS central AUTHORIZATION versola_app;
CREATE SCHEMA IF NOT EXISTS edge    AUTHORIZATION versola_app;
```

> Run the statements one at a time; pasting a block that mixes `psql` meta-commands (`\c`) with SQL
> leads to confusing parse errors.

The password is only ever printed on that first run (later runs reuse the stored one); it also stays
in `~/.versola/active/bundle-*/auth.secrets.env`.

> **Why separate schemas — do not skip this.** Flyway tracks applied migrations in a
> `flyway_schema_history` table *inside the schema it is pointed at*. Two services sharing one
> schema share one history table, and the second one to migrate aborts with
> `FlywayValidateException`. This is exactly how the first deployment failed — see
> [9.1](#91-flywayvalidateexception-on-startup-or-during-migrate).

### 3.4 Migrate

```bash
versola migrate
```

Applies `central`'s, `auth`'s and `edge`'s migrations from one throwaway `versola-tools` container.
Services never migrate on their own startup (`RUN_MIGRATIONS=false`, see
[`RUN_MIGRATIONS`](#run_migrations)).

### 3.5 Up

```bash
versola up
```

Starts `central`, then `auth` and `edge`, then `versola-proxy`, waiting for each to be ready, and
finally checks that a request through the proxy reaches `auth`. It ends by printing where the
admin's bootstrap password is ([First admin login](#the-admin-console-central-ui)).

`versola bootstrap vps <version> --auth-url … --postgres-host … --proxy external` runs 3.2–3.5 in
one go. On a first run that generates the Postgres password it **stops before `migrate`** (exit
code ≠ 0) so you can run the SQL from 3.3; continue with `versola migrate` and `versola up`.

### 3.6 Verify through the proxy

```bash
H='-H Host:id.versola.kz -H X-Forwarded-Proto:https'
curl -s -o /dev/null -w "%{http_code}\n" $H http://127.0.0.1:2821/.well-known/openid-configuration   # 200
curl -s -o /dev/null -w "%{http_code}\n" $H http://127.0.0.1:2821/central/admin/                     # 200
curl -s -o /dev/null -w "%{http_code}\n" $H http://127.0.0.1:2821/central/permissions/me             # 401
```

### 3.7 Host nginx

The `id.versola.kz` server block in the [`nginx`](https://github.com/versolauth/nginx) repo
(`envs/dev/versola.conf`) is only TLS plus one forward:

```nginx
server {
    server_name id.versola.kz;

    client_max_body_size 8m;

    location / {
        proxy_pass http://127.0.0.1:2821;
        proxy_http_version 1.1;
        proxy_set_header Host $http_host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_set_header Connection "";
    }

    listen 443 ssl http2;
    # ssl_certificate / ssl_certificate_key / includes managed by certbot
}
```

- `Host $http_host` — passed through as-is. Versola doesn't trust it: the issuer, redirect URLs and the DPoP `htu` come from configuration (`--auth-url`), and `versola-proxy`'s own redirects are relative.
- `X-Forwarded-For $proxy_add_x_forwarded_for` — `versola-proxy` trusts it only from `127.0.0.1`
  and restores the real client address from it; `auth` uses that address for rate limiting.
- `X-Forwarded-Proto $scheme` — the scheme the browser used; standard for a TLS-terminating proxy (the services themselves take the scheme from configuration).
- `client_max_body_size 8m` — the host nginx must allow the same body size as `versola-proxy`
  (themes, JWKS and resource definitions are POSTed through the console).

Change it through the `nginx` repo, not on the server: its workflow copies the file, runs
`nginx -t` and reloads on merge to `main`, so an in-place edit is silently reverted by the next
deploy of that repo. Other sites' blocks (`versola.kz`, `blog`, `docs`, `grafana`) are unrelated.

## 4. Deploying a new version

Images are built and pushed **only** by the `release: published` event — merging to `main` runs
tests but publishes nothing.

1. **Cut a release.** GitHub → Releases → *Draft a new release* → new tag (no `v`), target `main` →
   *Generate release notes* → *Publish*.
2. **Wait for the images.** In Actions, `docker-tools`, `docker-auth`, `docker-central` and
   `docker-edge` must all be green.
3. **On the host**, keep the CLI current and back up the database:
   ```bash
   versola upgrade
   (umask 077; sudo -u postgres pg_dump auth > ~/auth-backup-before-<version>-$(date +%Y%m%d-%H%M%S).sql)
   ```
   Migrations cannot be rolled back — the dump is the rollback.
4. **Configure, migrate, start** — same flags as the first time:
   ```bash
   versola configure vps <version> --auth-url https://id.versola.kz \
     --postgres-host 127.0.0.1:5432 --proxy external
   versola migrate
   versola up
   ```
   Each step asks for confirmation on `vps`. `configure` and `migrate` don't touch the running
   services; the outage is only the `up` itself (pulling images and recreating the containers — a
   couple of minutes). Migrations must therefore be compatible with the previous version, which
   keeps serving while they run.
5. **Verify** as in [3.6](#36-verify-through-the-proxy), then from outside:
   ```bash
   curl -s -o /dev/null -w "%{http_code}\n" https://id.versola.kz/.well-known/openid-configuration
   versola status
   ```

**Before migrating**, check that the release doesn't *edit* a migration that production has already
applied — only adding new ones is safe. In a `versola` clone with both tags (your workstation —
the host has none; `git fetch --tags` first), `git diff --name-status <old>..<new> --
'*/postgres/migrations'` must show only `A` lines. Without a clone, open
`https://github.com/versolauth/versola/compare/<old>...<new>` → *Files changed* and check that every
file under `postgres/migrations` is new. An edited one fails Flyway's checksum validation
and leaves no safe way forward except recreating that schema
([6](#6-recreating-the-database-from-scratch)).

**Rollback.** If the new release only *added* migrations and the previous version runs fine on the
newer schema, going back is just `versola configure vps <previous> …` + `versola up` (install the
matching CLI from GitHub Releases if needed). If the migrations must be undone, restore the database
**before** starting the previous version — never start it against a schema only the new release
understands:

```bash
versola down                                               # nothing may write while restoring
sudo -u postgres psql -c "DROP DATABASE auth;"
sudo -u postgres psql -c "CREATE DATABASE auth OWNER versola_app;"
sudo -u postgres psql -d auth < ~/auth-backup-before-<version>-<timestamp>.sql   # your shell opens the file, not postgres
versola configure vps <previous> --auth-url https://id.versola.kz \
  --postgres-host 127.0.0.1:5432 --proxy external
versola migrate                                            # no-op: the dump already has the previous schema
versola up
```

Anything written between the dump in step 3 and the rollback is lost — which is why the dump is taken
right before `migrate`.

#### Tag naming

The image tag is the git tag verbatim (`version=${{ github.event.release.tag_name }}` in
`ci-cd.yml`, no normalisation). Versola's releases carry **no** `v` prefix (`0.6.2`), and that is
the `<version>` `versola configure` takes. `versola-cli` uses the same format since `0.2.6` (its
older releases, up to `v0.2.5`, had the prefix).

### `RUN_MIGRATIONS`

`RUN_MIGRATIONS` controls whether a service applies Flyway migrations itself on startup:

- unset → **migrations do not run** — the service *validates* the schema against this build's
  migrations and fails to start if they're missing (see `PostgresHikariDataSource.layer`'s own
  comment). Applying a schema change is the deliberate, separate `versola migrate` step.
- `true` / `false` (lowercase, exact match) → as specified.
- anything else → the service **fails to start** with an explanatory error, deliberately.

The generated `compose.yml` sets `RUN_MIGRATIONS: "false"` on all three services.

## 5. Secrets and configuration

**Secrets** live in OpenBao, under `secret/versola/vps/{auth,central,edge}` (KV v2). The generated
`.conf` files hold only `${VAR}` placeholders; `configure` resolves them into `<service>.secrets.env`
in the bundle (mode `600`), which Compose passes to the containers. The services never talk to
OpenBao at runtime — it only has to be up for `configure`.

To change a secret: write the new value into OpenBao with `bao kv patch` (merges; `kv put` would
replace the whole path), then run `versola configure vps <current version>` with the same flags as
in [4](#4-deploying-a-new-version) — `--proxy external` included, or it defaults to `nginx` and
stops on ports 80/443 — followed by `versola up`:

```bash
docker exec -it -e BAO_ADDR=http://127.0.0.1:8200 -e BAO_TOKEN=<root token> versola-openbao-vps \
  bao kv patch -mount=secret versola/vps/auth SOME_KEY='<value>'
```

The root token is in `~/.versola/openbao/vps-admin.json`. The Postgres password is shared by all
three paths and must be identical in each — `configure` refuses to continue if they disagree.

**Non-secret configuration** (`auth.conf`, `central.conf`, `edge.conf`) is generated by
`versola-tools` for the release. There is not yet a supported way to change individual settings
(OTP provider, SMTP, …) on `vps`: an edit to the bundle's files takes effect after
`docker restart <service>` but is lost on the next `configure`. Configuration editing through the
CLI is planned. If you do edit a `.conf` by hand, keep it UTF-8 — HOCON cannot read UTF-16 (see
[9.12](#912-a-service-crash-loops-with-a-hocon-parse-error-after-a-restart)).

## 6. Recreating the database from scratch

Flyway is configured with `cleanDisabled(true)`, so the application cannot drop anything. Do it by
hand. In both cases **stop the stack first, then dump, then drop** — a dump taken while the services
still run misses whatever they write before they stop.

**A whole database:**

```bash
versola down                 # stop writes and release the connections
(umask 077; sudo -u postgres pg_dump auth > ~/auth-backup-$(date +%Y%m%d-%H%M%S).sql)
sudo -u postgres psql
```

```sql
DROP DATABASE auth;
CREATE DATABASE auth OWNER versola_app;
```

`DROP DATABASE` fails with *"is being accessed by other users"* while any service still holds a
connection, which is why the stack goes down first (OpenBao with it — see the note under
"A single schema" below). Recreate the three schemas as in
[3.3](#33-database-role-and-schemas), then `versola migrate` and `versola up`. `central` re-runs its
bootstrap and reseeds clients, roles, forms and the admin user.

**A single schema** (e.g. one whose migration history no longer matches the release):

```bash
versola down
(umask 077; sudo -u postgres pg_dump -Fc -n <schema> auth > ~/versola-backup-<schema>-$(date +%Y%m%d-%H%M%S).dump)
sudo -u postgres psql -d auth -c "DROP SCHEMA <schema> CASCADE; CREATE SCHEMA <schema> AUTHORIZATION versola_app;"
versola migrate
versola up
```

(`versola down` also stops OpenBao, which is in the same Compose project; `up` doesn't start it
again — it isn't needed at runtime, and the next `configure` brings it back.)

Everything configured by hand in that schema (clients, resources, roles…) is gone afterwards; only
what `central`'s bootstrap seeds comes back.

| Variable | Default | Meaning |
|---|---|---|
| `PORT` | `8080` | application port |
| `APORT` | `8082` | optional additional internal application port; used by auth Account Settings |
| `DPORT` | `8081` | diagnostics port: `/metrics`, `/liveness`, `/readiness` |
| `BIND_HOST` | — | address to bind; the vps compose file sets `127.0.0.1` |
| `CONFIG_PATH` | `/app/config/env.conf` | path to the mounted HOCON config |
| `RUN_MIGRATIONS` | `false` | apply Flyway migrations on startup (see [`RUN_MIGRATIONS`](#run_migrations)) |
| `JAVA_OPTS` | `-XX:+UseG1GC -XX:MaxRAMPercentage=75.0` | JVM flags |

Everything else — secrets, keys, database credentials, bootstrap data — lives in the HOCON file
and OpenBao ([5](#5-secrets-and-configuration)), not in environment variables.

### If a connection pooler is ever put in front of Postgres

`central` and `edge` both keep a connection parked on `LISTEN` — that is how a config change
reaches every replica, and how a revoked token stops being accepted before it expires. A pooler in
**transaction mode cannot carry `LISTEN`**: it hands each transaction whichever backend is free, so
the session the subscription was registered on goes back to the pool and no notification is ever
delivered.

So when `postgres.url` is pointed at a pooler, set `postgres.notifications-url` to a **direct**
Postgres URL in the same `postgres { }` block:

```hocon
postgres {
  url               = "jdbc:postgresql://pgbouncer:6432/auth?currentSchema=edge"
  notifications-url = "jdbc:postgresql://postgres:5432/auth?currentSchema=edge"
}
```

One direct connection per replica, which is what a listener needs anyway. (Session mode also
works, at the cost of pinning a backend per replica.) Getting this wrong does not fail quietly:
each service checks at startup that it can receive its own notification, and refuses to start with
an error naming this setting if it cannot.

## 9. Troubleshooting

These are real failures from production and from building the deployment, kept because each one
cost real time.

### 9.1 `FlywayValidateException` on startup or during `migrate`

```
Validate failed: Migrations have failed validation
Detected applied migration not resolved locally: ...
```

Two services are sharing one Postgres schema and therefore one `flyway_schema_history` table — each
sees the other's migrations as foreign. The generated configs pin every service to its own schema
(`?currentSchema=`); check the JDBC URL in the service's log.

A **checksum mismatch** (`Migration checksum mismatch for migration version …`) means a release
edited a migration production had already applied. There is no clean fix: recreate that schema
([6](#6-recreating-the-database-from-scratch)). This happened in September 2026 across all three
schemas; see the check in [4](#4-deploying-a-new-version).

`versola migrate --dry-run` currently reports *pending* migrations as a validation failure too
(`Detected resolved migration not applied to database`) — that one is a known bug in the dry run,
not a problem with the database; plain `versola migrate` applies them fine.

### 9.2 `central` crashes with `FileNotFoundException: forms/common.css`

The admin login forms under `central/src/main/resources/forms/` are *generated* by `central-ui`
(`npm run build:forms`) and are gitignored. If the image is built without that step, the files are
absent and `BootstrapService` fails the moment it tries to seed them — only on an empty database,
so the image looks fine until the first bootstrap. Fixed in CI (the `docker-central` job builds the
forms first); if you see this again, the CI step has been lost.

### 9.3 Container dies with no error in its own log

```bash
sudo dmesg | tail -20 | grep -i 'killed process'
```

If the kernel OOM-killed it, the JVM never got to log anything. The generated compose file sets no
`mem_limit` yet ([10](#10-known-gaps)), so with `network_mode: host` each JVM sizes its heap from
the *host's* memory — three services plus the host's own workload can overcommit it. A JVM-level
`OutOfMemoryError`, by contrast, *is* logged with a stack trace.

### 9.4 502 or 504 from `id.versola.kz`

Work inwards:

```bash
docker ps --format '{{.Names}}  {{.Status}}' | grep versola
curl -s -o /dev/null -w "%{http_code}\n" -H Host:id.versola.kz http://127.0.0.1:2821/.well-known/openid-configuration
curl -sf http://127.0.0.1:8091/readiness && echo central ok
curl -sf http://127.0.0.1:8081/readiness && echo auth ok
curl -sf http://127.0.0.1:8096/readiness && echo edge ok
```

- Nothing on `2821` → `versola-proxy` is down (`docker logs versola-proxy`; `versola up` starts it).
- Proxy answers 502 → the service behind it is down. Check `central` first: `auth` and `edge` block
  on their initial sync from it.

A bare `curl -sI https://id.versola.kz/` returning **404** is expected — there is no route at `/`.

### 9.5 `auth`/`edge` never become ready after restarting the whole stack together

**Status: fixed at the application level** — `ReloadingCache.make` retries the initial load (up to
2 minutes while `central` is unreachable, a few quick attempts for any other error), and a failed
startup now exits properly (`VersolaApp.run` re-fails so finalizers run; a watchdog halts the JVM
after `startupFailureShutdownTimeout`, 20s, if they hang), so `restart: unless-stopped` can fire.
While waiting, a service answers `/liveness` 200 and `/readiness` 503.

Before this fix, a service whose startup failed stayed up as a zombie: its diagnostics server kept
the JVM alive with no restart. To check for that on an older image:

```bash
docker inspect versola-auth --format='{{json .State}}'    # or versola-edge
```

`StartedAt` well in the past with `RestartCount` `0` means it never restarted. Confirm `central` is
ready, then `docker restart versola-auth`.

**Practical rule:** don't restart all three at once by hand — `versola up` already orders them.

### 9.6 `docker pull` / `configure` says the tag is not found

Check the prefix: Versola's image tags have no leading `v` (`0.6.2`). See [Tag naming](#tag-naming).
`docker buildx imagetools inspect ghcr.io/versolauth/versola-tools:<tag>` or the package page on
GitHub shows what actually exists.

### 9.7 Recovering a user event stuck in the outbox dead letter table

`central` propagates user changes to `auth` via an outbox (`central.user_outbox`) with retries;
after `user-outbox.max-attempts` failed attempts (5 in prod) the event is moved to `central.user_outbox_dead`
and **stops retrying permanently** — for example if `auth` was down when `central` started
dispatching.

```sql
SELECT id, user_id, event_type, attempts, failed_at, error FROM central.user_outbox_dead;
```

Once `auth` is ready, requeue by hand:

```sql
INSERT INTO central.user_outbox (id, user_id, event_type, payload, attempts, next_attempt_at)
SELECT id, user_id, event_type, payload, 0, NOW()
FROM central.user_outbox_dead
WHERE id = '<event-id>';

DELETE FROM central.user_outbox_dead WHERE id = '<event-id>';
```

`central`'s outbox processor picks it up on its next poll; `SELECT count(*) FROM
central.user_outbox_dead;` should drop by one.

### 9.8 OpenBao doesn't start after a reboot, or is sealed

OpenBao comes back **sealed** after every restart (no auto-unseal), and it mounts `openbao.hcl`
from a bundle directory — if that bundle has since been removed, the container can't start at all.
Neither affects the running services (their secrets are already in `*.secrets.env`); both only block
the next `configure`, and the next `configure` fixes both: it recreates the container from the
current bundle and unseals it with the key in `~/.versola/openbao/vps-admin.json`. Without that file
(or with `--setup-openbao`), unseal by hand:

```bash
docker exec -it -e BAO_ADDR=http://127.0.0.1:8200 versola-openbao-vps bao operator unseal
```

### 9.9 `configure` or `up` fails with "container name already in use"

A container with one of the fixed names exists under a *different* Compose project — `configure`
hits it for `versola-openbao-vps` (the only container it starts), `up` for `versola-auth`,
`versola-central` or `versola-edge`. That is — typically left over from a
deployment not made by `versola-cli`, or a container under an old project name. Check with `docker compose ls` and `docker ps -a`; stop and
remove those specific containers by name (nothing stateful lives in them: Postgres is native,
OpenBao's data is in its external volume) and run `configure` again.

### 9.10 The admin console shows 404 right after a deploy

The first open of `/login/central-admin` right after `versola up` has sometimes returned 404, while
a reload or another browser works. Under investigation (readiness gating); reload once.

### 9.11 Clicking through the console hits `413 Request Entity Too Large`

Both nginx layers must allow large enough bodies: `versola-proxy` allows 8 MB, and so must the host
nginx (`client_max_body_size 8m` in the `id.versola.kz` block, [3.7](#37-host-nginx)).

### 9.12 A service crash-loops with a HOCON parse error after a restart

```
'…' may not be followed by token: '' (if you intended '' to be part of a key or string value,
try enclosing the key or value in double quotes)
```

The config file is **UTF-16**, which HOCON can't parse — usually a hand edit on Windows (PowerShell's
`>` writes UTF-16 LE). A running service holds its already-parsed config in memory, so this only
shows at the next restart. Convert and restart:

```bash
b=~/.versola/active/$(python3 -c 'import json,os;print(json.load(open(os.path.expanduser("~/.versola/active/state.json")))["bundleDir"])')
iconv -f UTF-16 -t UTF-8 "$b/auth.conf" > /tmp/auth.conf && cp /tmp/auth.conf "$b/auth.conf" && docker restart versola-auth
```

Check all three — `file "$b"/*.conf` must say `ASCII`/`UTF-8` for each — and convert
`central.conf`/`edge.conf` too if needed, even if those services are currently up, or they'll
crash-loop on their next restart. Generated files are always UTF-8; a new `configure` also fixes
it.

## 10. Known gaps

- **No `mem_limit` on any service** in the generated compose file. With `network_mode: host`,
  `-XX:MaxRAMPercentage=75.0` is computed from the host's memory for each of three JVMs.
  `versola doctor`/`configure` check available memory first, which lowers the risk but doesn't
  remove it.
- **No supported way to change configuration on `vps`** — OTP provider, SMTP and similar settings
  can only be edited in the bundle, and the next `configure` discards the edit
  ([5](#5-secrets-and-configuration)). As a result **SMTP and SMS are not configured in prod**:
  password resets and additional admin accounts can't deliver a temporary password.
- **Single instance per service.** `container_name`s and ports are fixed; multiple replicas and
  rolling upgrades are planned in `versola-cli`. Until then each `versola up` of a new version is a
  short outage.
- **The host nginx block must be kept in the `nginx` repo** — a deploy of that repo overwrites the
  server's file. Keep [3.7](#37-host-nginx) and the repo in sync.
- **`versola migrate --dry-run` fails whenever there is something to apply** — see
  [9.1](#91-flywayvalidateexception-on-startup-or-during-migrate).
- **`configure` prints the OpenBao AppRole `role-id` and `secret-id`** on every run (by design,
  same UX as `local`), so they end up in terminal scrollback. OpenBao listens on `127.0.0.1` only.
- **Interactive host access is by password.** Engineers' own logins should move to key-based
  `authorized_keys` entries.
- **`central-ui`'s bundle filename isn't content-hashed** (minor) — handled with
  `Cache-Control: no-cache` (a cheap `304` per load).

## 11. Retired deployment path

Until September 2026 production ran differently. None of this is used any more; it is listed so old
references make sense.

- **The `Deploy` GitHub Actions workflow** (`.github/workflows/deploy.yml`) — deployed one service
  at a time over SSH by patching image tags in `/opt/versola/docker-compose.prod.yml` and copying
  configs from `env-config`; it also built `central-ui` and copied it to `/website/central-ui/dist`.
  **Removed** — running it now would start a second set of containers with the same names as
  `versola-cli`'s and take production down. Its repository secrets (`VPS_HOST`, `VPS_USER`,
  `VPS_SSH_KEY`, `VPS_HOST_FINGERPRINT`, `ENV_CONFIG_PAT`) should be deleted, the `ENV_CONFIG_PAT`
  token revoked (it can read `env-config`), and the `VPS_SSH_KEY` public key removed from the
  host's `authorized_keys`.
- **The `env-config` repository** — held the production `.conf` files, secrets in plaintext.
  Replaced by generated configs plus OpenBao. Its contents are stale; treat access to it as access to
  old production secrets until it is archived.
- **`/opt/versola/`** on the host (`docker-compose.prod.yml`, `config/*.conf`) and
  **`/website/central-ui/dist`** — no longer read by anything.
- **Versola routing in the host nginx** — the old `id.versola.kz` block routed `/central/…`,
  `/resources`, `/login`, … itself; that now lives in `versola-proxy`.
