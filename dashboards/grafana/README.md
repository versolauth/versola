# Grafana dashboards

Boards, all generated by `generate.py`:

- `versola.json` (uid `versola`): the system under test, auth, central and edge, with the ingress's key tiles on top.
- `versola-db.json` (uid `versola-db`): the database as the services see it (pool, queries, WAL, table sizes, cleanup). Pick the service at the top.
- `versola-ingress.json` (uid `versola-ingress`): ingress-nginx in full (needs the controller's metrics scraped).
- `versola-antifraud.json` (uid `versola-antifraud`): the antifraud module of auth, see its section below.
- `loadgen.json` (uid `versola-loadgen`): the load generator, see the last section.

`versola.json` is one board for the whole system: auth, central and edge.

1. **Overview** — two lines of four tiles per service (pods, requests, 5xx share, p99, two
   service-specific tiles, DB pool, heap). Green/yellow/red; read this first.
2. **A section per service** — traffic, errors and latency per endpoint, then the service's own
   signals: auth (sign-in funnel, token refresh), edge (resources, web, mobile `/native`, token
   revocation), central (config syncs, admin writes, change notifications). The database and
   runtime rows are collapsed.

Nothing on it concerns the load generator. Each service also has a row for overload protection (in flight against the limit, what was refused, the adaptive limit, executor lag) and, for edge and auth, one for rate limits (refused and would-be-refused by policy, share of calls refused, keys tracked, pods the limit is divided by, where the caller address comes from); the outbound guard (queue, refusals, circuit breaker, retries denied) is in each service's collapsed "Calls to other services" row. It also holds the outbound pool (`http_client_active_requests` by
peer), connection timeouts, the WAL section (rates, checkpoints, slots, records), Argon2 admission (queue, permits, wait) in auth, and cleanup removal rate and staleness.

## Selectors and percentiles

- **Env** is the namespace; **Tail quantile** is p99, p99.9, p99.99 or p99.999; the database board adds **Service**.
- A graph that answers "how is latency?" for a whole service, the ingress or the database draws p50, p95 and p99, plus the tail quantiles up to the selected one (p99: none extra; p99.99: p99.9 and p99.99). A tile, or a graph with a series per endpoint, query, peer or grant, follows Tail quantile alone. p99.99 needs roughly 10 000 requests in the rate window and p99.999 roughly 100 000, and both are rounded up to the histogram's bucket edge.
- Host metrics of the database (CPU, disk, replication) are not on these boards; they come from the database platform.

## Loading it

Import `versola.json`, `versola-db.json`, `versola-ingress.json`, `versola-antifraud.json` and `loadgen.json` in Grafana (Dashboards → New → Import), or provision it from a ConfigMap
with the label your Grafana sidecar watches. The only variables are the Prometheus data source and
the namespace. The dashboard's uid is `versola`, so importing it again overwrites it.

## What it expects from the scrape

Series are selected by `namespace` and `app_kubernetes_io_component` (the pod label
`app.kubernetes.io/component`, `auth|central|edge`). All three services are scraped under one `job`,
so `job` cannot tell them apart; the scrape configuration must copy pod labels onto the series
(`labelmap`, as in [`k8s/monitoring/vmagent-values.yaml`](../../k8s/monitoring/vmagent-values.yaml)).

The WAL section of each service is read from that service's own database (`pg_stat_wal`, `pg_stat_checkpointer`,
`pg_settings`, `pg_replication_slots`) by the service itself, once a minute, so no `postgres_exporter` is needed. The
database role the service uses needs no extra privilege for it; a view it cannot read is logged once and left out. Where
the three services share one database, the three sections show the same numbers.

Some panels are empty by design until their source exists: the database pool panels need
`postgres.pool-metrics-interval`, the "Edge overhead (measured)" panel needs `edge_proxy_overhead_seconds`,
and the panels that count failures are empty while nothing fails.

## The load generator board

`loadgen.json` selects series by `namespace` only (the loadgen chart's own release; its pods carry no service
label) and its namespace variable lists the namespaces that publish `loadgen_campaign_info`. Rows: Campaign (the
refresh:code ratio, exchange rates, schedule lag, driver CPU), Load, Emulator health, Mock backend.

The ratio tile and graph divide `token-refresh` by `token-code` step counts (every scenario, every outcome). The
target profile is 5 to 10; green inside it, red below, yellow above. The tile covers the selected time range, warm-up
included; the campaign report states the same figure over the measured phases as `refreshToCodeRatio`
(`{refreshes, codes, ratio}`). To reach the target, set `session.refresh-count.mobile-mean` (see
`k8s/loadgen/values.yaml`).

## The antifraud board

`versola-antifraud.json` selects series from `auth` (`namespace` and `app_kubernetes_io_component="auth"`), with the same Env and
Namespace variables and no tail quantile. Rows, top to bottom: Decisions (rate by would-be action, the share the rules would stop, what
was acted on next to what was decided, evaluation failures), Rules (the most frequent, those that count and those that only record),
Challenges (by kind and outcome, proof-of-work pass rate, pause paid share), SMS budget (refused by reason and mode, ranges not tracked or
evicted), Event pipeline (enqueued, written, dropped by reason, queue size, backlog growth), Velocity, Lists (hits with the shadow split,
refresh failures, snapshot and tuning age), Detectors and resets, Storage (partition days ahead with a line at 2, maintenance and rollup
failures, database latency and failures of the antifraud operations, `operation=~".*antifraud.*"`).

Read it in shadow mode as: the would-be share in Decisions is what enforcing would stop, and "let through, would be stopped" is the part of
it that was only recorded. Every failure panel is empty when healthy. Alert rules for the same signals are in
[`../alerts/`](../alerts/README.md). The board uses metrics that are only on `main` once the antifraud shadow and store changes
are (`antifraud_decisions_total{would_action}`, `antifraud_rules_fired_total`, `antifraud_evaluation_failed_total`, the refresh timestamps,
`antifraud_partition_days_ahead` and others); a panel on a metric that is not there yet stays empty.

## Changing it

The JSON is generated. Edit `generate.py`, run it, commit it and the boards:

```bash
python3 dashboards/grafana/generate.py
```

A threshold is drawn only where a number is defensible without a written SLA.
